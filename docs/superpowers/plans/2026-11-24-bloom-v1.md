# BLOOM v1 (Functional Web App) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> Execution method for this build: **native** (owner said "make it"; harness forbids unrequested subagents). Commits only when the owner asks.

**Goal:** Ship the owner's Phase 1 web app — Mochi (3D, everywhere) with a real AI backend, period tracking with honest uncertainty, wellness basics, Bloom Shield with an offline emergency path, and Bloomverse — built so real women can test it.

**Architecture:** Next.js 16 App Router, server-rendered per request (no Cache Components). Server Components read through a small data-access layer that enforces the session and decrypts per-user payloads; mutations go through Server Actions or Route Handlers that re-check the session. 3D runs in two isolated R3F canvases (corner Mochi, Bloomverse). The emergency layer depends on nothing but HTML links and a precached static page.

**Tech Stack:** Next.js 16.4, React 19.3, TypeScript, Tailwind 4, Motion 14, R3F 9 + drei 10 + three 0.187, Drizzle 0.45 + PostgreSQL 16, Better Auth 1.7 (+ passkey plugin), AI SDK 7 (Anthropic/OpenAI/Google), web-push, Radix primitives, Vitest 5, Playwright 1.65 with the system Chrome.

**Spec:** `docs/spec/master-prompt.md` + `docs/spec/additions.md` (additions win on conflict).

## Global Constraints

- Node ≥ 20.9; browsers Chrome/Edge/Firefox 111+, Safari 16.4+.
- Palette exactly: Bloom Pink `#FF4F91`, Rose Red `#E83F65`, Soft Blush `#FFF0F5`, Cherry Coral `#FF667A`, Petal Pink `#FFB8D0`, Cream White `#FFF9F7`, Deep Berry `#66263F`, Lavender Mist `#EADCF8`.
- Themes: light, dark, discreet ("Daybook"), high contrast; motion: system / reduced / full; text scale 100/115/130 %.
- India default emergency number **112**; never claim an alert was delivered without a receipt; never claim autonomous emergency dispatch.
- AI never diagnoses, never claims to be human or a clinician, gets no tools, and never sees cycle data or memories without the matching consent.
- No hard-coded AI replies: when no provider is configured the chat says so.
- All health payloads (cycle days, moods, journal, memories, emergency info, contact details, locations, destinations) are stored only as `sealJson` ciphertext.
- Copy: sentence case, plain verbs, no ALL-CAPS labels, no `→` in buttons, errors say what happened and what to do.
- Predictions are labelled estimates; fertile-window display is opt-in and always says "Not a method of contraception."
- Every interactive control has an accessible name; focus is visible; touch targets ≥ 44 px; animations respect reduced motion.

## Review Focus

1. **SOS with the network down or the server erroring** → manual Call 112 / Text contacts actions are on screen before any fetch resolves, and the status line says alerts were *not* sent. (Task 9: `sos-flow` e2e offline test + `sosReducer` "dispatch failed" test.)
2. **Cycle logs with gaps, spotting-only days, or a single logged period** → no crash, no false precision: prediction status/confidence match the data. (Task 6 tests `gap of one unlogged day stays one period`, `spotting alone never starts a period`, `one period gives no history prediction`.)
3. **Another user's IDs in requests** (contact id, journey id, SOS id, journal id) → 404, never data. (Task 4 `repositories enforce owner` integration test; Task 9/10 route tests.)
4. **Crisis or emergency language when AI is unconfigured or the provider fails** → deterministic safety card still appears. (Task 7 `chat route returns safety card without provider`.)
5. **Low-end device / no WebGL / reduced motion** → Mochi and Bloomverse fall back to static SVG; SOS never waits on 3D. (Task 8 `fallback renders when WebGL is unavailable` component test; Task 12 e2e with `--disable-webgl`.)
